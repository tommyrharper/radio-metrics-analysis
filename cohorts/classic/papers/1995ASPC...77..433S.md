# A Retrospective View of Miriad

**Bibcode:** 1995ASPC...77..433S
**Authors:** R. J. Sault, P. J. Teuben, M. C. H. Wright
**ADS:** https://ui.adsabs.harvard.edu/abs/1995ASPC...77..433S/abstract
**arXiv:** https://arxiv.org/abs/astro-ph/0612759
**Full text:** https://arxiv.org/pdf/astro-ph/0612759

## One-line summary
The authors retrospectively describe Miriad as a full-service radio-interferometry reduction package spanning raw visibility ingestion, imaging, deconvolution, image analysis, and publication-quality output, and explain how its modular interface, flexible native visibility format, portability layer, and relatively small scope supported rapid algorithm development.

## Method
Miriad was designed to take raw interferometer data through image analysis rather than implement a single imaging algorithm. Its front end is separated from the number-crunching tasks: a front end supplies documentation and assembles parameters, while tasks receive those parameters as command-line arguments and can also be invoked directly or from host-shell batch scripts. Task and subroutine documentation is embedded in source-code preambles and extracted automatically when code is compiled.

For data handling, Miriad uses an image data-set structure that closely shadows FITS, making image translation straightforward, but it does not use uv FITS as its native visibility representation. Instead, its visibility format derives from the RALINT design and was chosen to support forms of visibility data that the authors considered difficult to represent in uv FITS. Data are stored in a canonical machine-independent on-disk form, with conversions hidden inside the I/O layer. The I/O system and ancillary tools are written in C, most application code is written in FORTRAN, and a generated thin interface layer adapts the FORTRAN-to-C boundary to each system. PGPLOT supplies plotting facilities and some numerical code uses LINPACK.

The package was also integrated into the Hat Creek interferometer's online system: that system shared Miriad's interface and documentation framework and wrote raw observations directly in Miriad's uv format. The paper presents this end-to-end architecture and its design history, not an experimental comparison of imaging or deconvolution algorithms.

## Performance / fidelity metrics used
- **No quantitative image-fidelity metric is defined or reported.** The paper contains no PSNR, SNR, dynamic-range, residual, flux-recovery, astrometric, or deconvolution-accuracy measurements.
- **No runtime, throughput, memory, scaling, or hardware benchmark is reported.** The authors say that the native visibility format is more flexible than the FITS-style alternative and has a cleaner programmer interface, but also that its then-current implementation can be slow to read; no read rate or baseline timing is given.
- **Portability is assessed qualitatively.** Miriad is said to have been ported with minimal effort to many UNIX-based systems. The paper notes six system-dependent FORTRAN-to-C calling schemes handled by its generated interface layer, but provides no portability success rate or engineering-time measurement.
- **Development speed is assessed qualitatively against AIPS.** The authors state that Miriad became useful comparatively quickly and could be extended with new algorithms at a good rate, while AIPS programming overhead would have slowed or prevented some applications. These are retrospective judgments, not controlled measurements.
- **Usability and visualization are also qualitative.** Separate front ends, direct shell invocation, automatically generated documentation, and integration from telescope control to publication output are presented as advantages. Image display is explicitly described as a weakness: the interim routines remained basic, and PGPLOT's display model was limiting. No user study or visualization-quality score is supplied.

## Relevance to visibility→gridding→iFFT→deconvolution ML pipeline
Miriad is relevant as an early end-to-end systems baseline rather than as an ML method or a source of imaging-quality metrics. Its native visibility layer, command-line task boundaries, FITS-compatible image representation, imaging and deconvolution tasks, and image-analysis stage expose the same broad pipeline boundaries that a visibility-to-image ML workflow must integrate with. The paper also highlights long-lived engineering concerns for such a pipeline: flexible visibility metadata, portable and machine-independent I/O, scriptable task interfaces, and the tradeoff between a compact extensible package and a larger general-purpose system. It does not evaluate gridding kernels, iFFT accuracy, deconvolution fidelity, or learned reconstruction, so those properties should not be attributed to this source.
